# ARCHITECTURE.md — как устроен OPORA

Это описание того, что есть в коде сейчас, и того, куда встанут оставшиеся этапы. Продукт — в `OPORA — план приложения.md`, внешний вид — в `DESIGN.md`.

Одна фраза: **один процесс, один экран, один файл SQLite.**

---

## 1. Зависимости между файлами

```
main.rs ──► app.rs ──► theme.rs
             │
             └──► lib.rs (db, entry) ──► %APPDATA%\Opora\opora.db
```

Стрелки только в одну сторону. Главное условие: **`lib.rs` не знает про egui**. Поэтому `opora-mcp` (этап 6) сможет подключить `db` и `entry`, не таща за собой графический стек.

| Файл | Роль | Знает про | Не знает про |
|---|---|---|---|
| `main.rs` | окно, wgpu (только DX12), открытие базы | eframe, `db` | форму, SQL |
| `app.rs` | состояние экрана, отрисовка, сценарии «загрузить день» / «сохранить» | egui, `db`, `entry`, `theme` | SQL-запросы, формат файла базы |
| `theme.rs` | палитра, шрифты, стиль виджетов | egui | данные |
| `entry.rs` | модель дня и её правила | chrono | egui, rusqlite |
| `db.rs` | путь, открытие, схема, upsert, чтение | rusqlite, `entry` | egui |
| `export.rs` | *(этап 4)* `.md` и `.csv` из набора записей | `entry` | egui, БД |

`lib.rs` — это ядро. Оно маленькое намеренно: всё, что нужно и приложению, и будущему MCP, живёт здесь; всё, что нужно только окну, — в `app.rs`.

## 2. Правила ядра

`entry.rs` — единственное место, где решается, что запись корректна:

- `mood` ∈ 1..=10, обязателен;
- `sleep_hours` — либо `None` («не помню»), либо 0..=24;
- дата на границе с БД — строка `%Y-%m-%d`, внутри — `NaiveDate`.

Валидация стоит здесь, а не в форме и не в SQL, потому что данные будут приходить с двух сторон: из окна и из MCP. Проверка в UI защищает только UI.

`db.rs` не валидирует, а вызывает `entry.validate()` перед `INSERT`. Ошибка возвращается наверх как `anyhow::Error`.

## 3. Поток одного дня

```
старт:   main → db::open_default → App::new → db::load(today) → форма заполнена
сохранить: клик → parse_sleep → Entry::new (валидация) → db::save (upsert) → «сохранено в 21:34»
```

Оба пути синхронные. Локальный файл отвечает за микросекунды; `async`, пул соединений и фоновые задачи здесь были бы дороже, чем сама работа.

## 4. Состояние экрана

`App` держит одно соединение и черновик формы:

| Поле | Тип | Почему так |
|---|---|---|
| `conn` | `Connection` | одно на процесс, живёт столько же, сколько окно |
| `date` | `NaiveDate` | день, который сейчас редактируется |
| `sleep_text` | `String` | пользователь печатает «7,5»; `f32` не даёт набрать промежуточное «7,» |
| `sleep_unknown` | `bool` | «не помню» — это `NULL`, а не ноль |
| `mood` | `u8` | шкала 1–10, всегда валидна |
| `note` | `String` | одна строка |
| `status`, `error` | `Option<String>` | что показать под формой |

Граница «текст формы ↔ `Entry`» проходит ровно в двух местах: `parse_sleep` (разбор числа, запятая как разделитель) и `Entry::new` (правила). Между ними формы не существует — поэтому и не нужен отдельный слой моделей.

Отрисовка — одна функция `eframe::App::ui`. В immediate mode состояние живёт в полях структуры, а не в дереве виджетов, поэтому «сохранить» — это метод `&mut self`, а не обработчик события.

## 5. Хранилище

Одна таблица, одна запись в день:

```sql
CREATE TABLE entries (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  date       TEXT NOT NULL UNIQUE,   -- 'YYYY-MM-DD'
  sleep_hours REAL,                  -- NULL = не помню
  mood       INTEGER NOT NULL,       -- 1..10
  note       TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

Инварианты:

- `date UNIQUE` + `INSERT ... ON CONFLICT(date) DO UPDATE` — повторное сохранение правит день, а не плодит дубли;
- `created_at` в upsert не участвует: дата первой записи не перезаписывается;
- `sleep_hours = NULL` и `sleep_hours = 0` — разные вещи, и это видно в схеме.

`PRAGMA journal_mode = WAL` включён не «для скорости», а чтобы второй процесс (MCP) читал базу, пока приложение пишет.

Миграций пока нет: схема создаётся через `CREATE TABLE IF NOT EXISTS`. Первое настоящее изменение схемы — это явный шаг через `PRAGMA user_version`, а не `ALTER TABLE` вслепую при старте.

## 6. Ошибки

Вниз — `anyhow::Result`. Наверх, в окно, — строка: `App` кладёт её в `error` или `status` и продолжает работать. Экран не должен падать из-за того, что в поле сна написали «много»; приложение, которое закрывается с ошибкой, не открывают на следующий день.

## 7. Отрисовка и DPI

Всё меряется в поинтах, egui сам переводит их в пиксели по масштабу системы. Колонка контента — фиксированной ширины по центру окна, поля окна 32 pt.

Открытая проблема (из журнала плана): при масштабе 125% правый край колонки обрезает день недели и строку заметки. Это дефект раскладки, а не шрифта, и чинить его надо отказом от жёсткой ширины, а не подбором числа под текущий монитор. Проверка — на 100% и 125%.

## 8. Куда встают оставшиеся этапы

| Этап | Что добавляется | Файлы | Что не меняется |
|---|---|---|---|
| 2. Список | `db::recent(conn, 30)` → `Vec<Entry>`; клик по строке грузит день в форму | `db.rs`, `app.rs` | схема, `entry.rs` |
| 3. График | точки из того же `recent()`, пустое состояние «пока нет данных» | `app.rs` | `db.rs` |
| 4. Экспорт | `to_markdown`/`to_csv` как чистые функции `&[Entry] -> String`, запись файла — на краю | новый `export.rs` | `app.rs` (только кнопка), схема |
| 5. `.exe` | `cargo build --release` | — | всё |
| 6. MCP | `src/bin/opora-mcp.rs`: те же `db` и `entry` | новый бинарь | `app.rs`, схема |

Ключевое следствие: список и график берут данные из одного запроса, экспорт — из того же `Vec<Entry>`. Ни один из этапов не требует менять модель.

## 9. Где проходит шов для тестов

- `entry.rs` — чистые функции, без БД и без времени (кроме `today()`).
- `db.rs` — интеграционные тесты в `tests/db.rs`, только на `tempfile::tempdir()`; настоящая база не трогается никогда.
- `app.rs` — сценарии (`save`, `load_day`, разбор сна) тестируются на структуре без окна: egui-контекст нужен только конструктору.
- `export.rs` — сравнение строк; один тест на реальный файл во временной папке.

Правило простое: если функцию нельзя проверить без окна, значит логика попала не в тот файл.

## 10. Чего здесь нет и не будет

Трейтов-репозиториев, внедрения зависимостей, `Arc<Mutex<_>>`, async-рантайма, шины событий, плагинов, таблицы настроек, фреймворка миграций, i18n, телеметрии, сети.

Каждая из этих вещей решает проблему, которой у приложения с одним экраном и одним файлом нет.
